一、用户要什么（这是唯一的权威口径，与本文档其他部分冲突时以此为准）
================================================================================

原文：

  "原生压枪只有个压枪强度，而我的只是把原生的压枪强度给拆分了而已。
   反正我的压枪参数设计就没有什么力度，我都不知道力度是哪来的，
   应该只有压枪速度和下压范围。
   而且连点和长按都是可以用的，就这么简单。"

翻译成需求：

  压枪只应该有两个参数：
    1) 下压范围  —— 最多压到多深（上限）
    2) 压枪速度  —— 压下去多快（速率）
  这两个参数【长按（按住不放）和连点（半自动点射）都适用】，不分模式。
  【不要有"力度"这个概念。】面板上不该出现"长按下压力度""连点下压力度"
  这类东西，也不该出现"长按XX""连点XX"这种成对的前缀。

  目标面板形态（大概）：
    压枪            [开关]
    下压范围        [滑块]   长按连点都适用
    压枪速度        [滑块]   长按连点都适用
    开火重置间隔    [滑块]   （已有，保留）

二、上游（原生）是怎么做的 —— 事实，已核对源码
================================================================================

上游仓库：https://github.com/xiangsu1145/Auto-aim_android-yolo/
本地可直接查看：git show origin/master:<path>
（本仓库的 origin 远端就是上游；包名是 team.maodie.aimbot，本 fork 改成了
 io.github.love3025.yolovaim）

上游全部压枪代码就这一段
（origin/master:app/src/main/java/team/maodie/aimbot/controller/AimController.kt:206-217）：

    fun executeAiming(targetX: Float, targetY: Float, cx: Float, cy: Float) {
        var adjustedTargetY = targetY
        if (recoilEnabled) {
            if (triggerHeld) {
                recoilOffsetY += recoilStrength * 3f
                adjustedTargetY += recoilOffsetY
            } else {
                recoilOffsetY = 0f
            }
        }
        ...
    }

上游只有一个参数 recoilStrength（0.0~1.0），事实清单：

  1. 它本质是【速率】：每帧累加 recoilStrength * 3f 像素。
     30fps 下 = strength * 90 px/s（strength=1.0 → 90px/s）。
  2. 【完全没有上限】。上游没有 MAX_OFFSET 之类的东西（git grep 已确认为 0 处）。
     所以"能压多深"只由"按了多久"决定 —— 这就是用户说的"强度好像是范围+速度
     的总和"：一个旋钮同时决定了压得多快和（因为无上限）压得多深。
  3. 门控是 triggerHeld，写在
     origin/master:.../service/FloatService.kt:1185：
         aimController.triggerHeld = touchService.isFingerInFireZone()
                                     || triggerController.triggerFired
     也就是【手指在开火区的电平】。因此上游本来就是"长按连点都适用"：
     连点时手指按下的那几十毫秒，斜坡照样在走。
  4. 松开立即清零（无衰减、无重置间隔）。
  5. 它写在 executeAiming() 里 —— 只有选中目标那一帧才推进。
     没目标时偏移量冻结不动（这是个真 bug，本 fork 已修，见第四节）。

结论：用户的"我只是把原生的强度拆开了"完全成立，而且拆得对：
把一个混合量拆成【速率】+【上限】两个独立量，是正确的方向。

三、当前分支的状态 —— 【它偏离了第一节的目标，需要你把参数收敛掉】

当前实现的是一套【2x2 对称参数】，也就是用户明确否掉的那套：

  |      | 力度                    | 速度                       |
  |------|-------------------------|----------------------------|
  | 长按 | recoilStrength          | recoilSpeed                |
  | 连点 | recoilTapStrength       | recoilTapSpeed             |

面板现在是五项：
  长按下压力度 (压到多深) / 长按下压速度 (每秒)
  连点下压力度 (每枪)     / 连点下压速度 (每枪落位)
  开火重置间隔

【这不是用户要的。】用户不要"力度"，不要"长按/连点"分开的参数。
要收敛到第一节那两个参数 + 开火重置间隔。

需要你处理的具体偏离点：

  (A) 参数要砍。现有四个 recoil* 滑块参数要收敛成两个：
      - 保留一个"下压范围"（上限）
      - 保留一个"压枪速度"（速率）
      - recoilTapStrength（连点每枪固定量，TAP_KICK_MAX_PX 那一套）
        和 recoilTapSpeed（连点落位 τ，TAP_TAU_* 那一套）按用户口径应当去掉。
      注意 config.json 的 key 兼容：recoilStrength 这个 key 从上游延续至今，
      不要改名，否则老配置读不到。删掉的 key 留着不读也无害。

  (B) HOLD_ONSET_MS = 150ms 这道"起步门限"必须【删掉】。
      它的作用是"按下不足 150ms 的算点一下、不走斜坡"，目的是把连点和长按
      分开。在用户的设计里连点也要吃速度和范围，所以这道门限会让连点几乎
      拿不到补偿（连点的按压时长典型 40~120ms，全在门限之下）——
      与目标直接冲突。

  (C) 偏移量目前拆成了 holdOffsetY + tapOffsetY 两份分开累计、各有上限。
      统一成一个参数后，这个拆分大概也该合回单个 recoilOffsetY + 单个上限。

  (D) 面板文案要重写（GuiPanelView.kt 的 buildAimbot()，约 244-256 行）。

四、本 fork 相对上游已经做对、【不要退回去】的部分
================================================================================

这些是之前几轮工作的成果，与第一节的目标不冲突，请保留：

  1. 【生命周期解耦】压枪状态机是独立的 updateRecoil()，由 FloatService 每推理帧
     无条件调用一次（FloatService.kt:1591），不再挂在 executeAiming() 上。
     上游挂在 executeAiming 里，导致"画面没目标时偏移量冻结"。

  2. 【时间基而非帧基】按 dt 累加（px/s），不是每帧固定量。
     上游是每帧 strength*3f，提帧后压枪同比变快；现在帧率无关。

  3. 【屏幕空间标度，不按目标框高】
     range/rate 都是屏幕高度的比例或绝对 px。历史上有个提交（7a1e202）改成
     按目标框高取比例，导致远距离（实测框高 15~20px）上限塌到 17px、速率塌到
     2.4px/s，比上游慢 37 倍，等于远处自动关掉压枪。8cef4fe 已改回屏幕空间。
     【不要再改回按框高取比例。】枪口爬升是镜头旋转，屏幕位移像素由 FOV 和
     分辨率决定，与目标远近无关；框高与距离强相关。这与 aimOffsetYRatio /
     boxAimRatio 是不同性质的量（那两个决定"打身体哪个部位"，该随框高缩放）。

  4. 【有上限】上游无上限，本 fork 有。RANGE_MAX_RATIO = 0.37（满量程 = 0.37 屏高，
     1080p 约 400px），MAX_OFFSET = 600px 作为绝对保险。
     "下压范围"这个滑块就是这个上限。

  5. 【松手不立即清零，走衰减 + recoilResetIntervalMs 重置间隔】
     上游松手立刻归零，半自动连点每枪都从 0 压起。现在超过 recoilResetIntervalMs
     才开始指数衰减。衰减而非硬清零是因为 offset 可累到上百 px，一帧归零会让
     errorY 跳变，PID 的微分项会直接吃到（applyDragSafety 管总位移、不管每帧
     速率，挡不住这个尖峰）。

  6. 【注入层数开火上升沿】连点的枪数由 native 层在 SYN_REPORT 上数上升沿
     （touch_core.cpp 的 countFireEdgeLocked / g_fire_taps，120-240Hz），
     应用侧一次 IPC 同时取走电平和枪数（touch_consume_fire_state 返回
     (taps<<1)|level）。若只按推理帧率查电平，30fps 下短于 33ms 的点击会整帧
     落空。即使去掉"每枪固定量"，这个枪数信号仍然有用（见第六节）。

  7. 【pow → exp】衰减用 Math.exp(dt * DECAY_EXP_PER_SEC)，
     DECAY_EXP_PER_SEC = -10.70024 = 30*ln(0.7)，与原来 pow(0.7, dt*30) 数学等价
     （float32 下偏差 3e-7）。实测 aarch64 OpenJDK：pow 97.3ns vs exp 19.3ns。
     纯性能，行为不变。

  8. 【resetRecoil() 要连 pendingKick 一起清】否则残量下一帧被加回刚归零的偏移。

  9. 【speed 系数 coerceIn(0f,1f)】面板滑块本就是 0~1，这道夹取守的是手改
     config.json 的情形（负值会让斜坡反向爬升）。

================================================================================
五、实测数据 —— 重新推导很贵，直接用
================================================================================

方法：用 Python 复刻 updateRecoil 的状态机，逐 1ms 推进手指电平、按 30fps 采样帧。
（本地【没有 Android SDK】，无法编译，只能靠仿真 + CI 验证，见第七节。）

5.1 "斜坡跟着手指电平走"会让每枪的量随按压时长漂移
    条件：5 发/秒、速率 90px/s、每枪固定量 20px、上限未触及
      按压 40ms  → 5 枪累计 118px
      按压 60ms  → 121px
      按压 90ms  → 133px
      按压 120ms → 148px
      按压 150ms → 163px      极差 45px (38%)
    注意：这个漂移【是上游的缺陷】，根源是"斜坡挂在开火电平上"。上游有这个毛病
    不等于可以照抄 —— 本 fork 的定位是纯优化，所以第六节的首选方案就是把它修掉。
    方向还是反的：决定总爬升的是开枪次数，不是按压时长，点得快反而每枪压得少。

5.2 连点的等效补偿速率 = 每枪的量 × 点击频率（若采用"每枪固定量"模型）
      3 发/秒 → 60px/s      5 发/秒 → 100px/s      8 发/秒 → 160px/s
    也就是说连点的 px/s 由玩家手指决定并自动缩放，天然低于全自动 —— 本该如此，
    开枪次数少枪口爬升就少。

5.3 单份 kick 的"落位"快慢被帧周期顶死（若采用"每枪固定量 + 指数释放"模型）
    30fps 一帧 = 33ms：
      τ=12ms  → 首帧就交付 94%（≈ 阶跃输入）
      τ=20ms  → 81%
      τ=36ms  → 60%   （历史上写死的值，= pow(0.4,dt*30) 的等效 τ）
      τ=120ms → 24%
    含义：想让连点"更快"没有余量，默认已贴着帧率下限；有真实行程的只有"更慢
    更柔"那一侧。而"多柔"该由 Y 轴 kp/kd 决定（kpYRatio/kdYRatio 被特意压低来
    抑制纵向震荡），是控制环的稳定性参数。
    → 这就是"连点下压速度"这个滑块可用行程很小的原因。用户要统一参数，这条
      正好支持把它删掉。

5.4 【开火重置间隔的陷阱】
    recoilResetIntervalMs 默认 300ms。慢速连点时，上一枪的补偿在下一枪到来前
    就衰减掉了：2 发/秒 + 300ms 间隔，实测等效速率只剩 3.1px/s（几乎等于没有）。
    重置间隔必须大于两枪的间隔才能累积。
    用户当前设的是 50ms（见 5.5），比这更激进。

5.5 用户设备上的实际配置（改之前，供你判断影响面）
      recoilEnabled: true
      recoilStrength: 0.51
      recoilTapStrength: 0.5
      recoilSpeed: 1.0          ← 速度拉满
      recoilResetIntervalMs: 50 ← 很短
    速度拉满意味着他之前在很大程度上依赖"斜坡跟着按压走"那条路径
    （速率 150px/s × 按压 60~150ms = 每枪偷偷多压 9~22px）。
    任何改动都要考虑他这套值下的手感变化，并告知他需要重调。

六、需要你决定/实现的核心问题
================================================================================

在"只有速度和范围、长按连点都适用"的前提下，【斜坡按什么规则推进？】
这是唯一真正需要设计的点。注意：下面所有方案都建立在第四节那九条优化【之上】，
只是"什么时候让斜坡往前走"这一个判据不同。不存在"回退到上游"的选项。

  方案 A：最短保持（latch）—— 【推荐】
    开火电平为真时推进斜坡；同时，每检测到一次开火上升沿，就把"正在开火"这个
    状态强制拉住至少 W 毫秒（W 为内部常数，例如 150ms），与手指实际按了多久无关。
    实现位置建议在 FloatService 算 recoilHeld 的那一行（:1587）做 latch，
    AimController 可以不改；上升沿计数用第四节第 6 点那个已有的 native 信号。
      · 长按：电平一直为真，latch 不起额外作用，行为 = 恒速斜坡到上限，不变。
      · 连点：每枪推进量恒为 速率 × W，与按压时长无关 —— 修掉 5.1 那 38% 的漂移。
      · 参数仍然只有速度 + 范围，两种开火方式都吃，符合第一节。
    要注意的实现细节：latch 不能把"松手"这件事也吞掉，否则
    recoilResetIntervalMs 的回落判断会失效；latch 只影响"斜坡是否推进"。

  方案 B：纯电平门控 —— 只在手指真的按着时推进斜坡。
    这是上游的判据（也是本 fork 目前 held 电平的来源）。
    优点：改动量最小，不需要上升沿信号。
    缺点：【继承了上游的缺陷】—— 每枪推进量 = 速率 × 按压时长，按得久压得多，
          实测漂移 38%（5.1）。本 fork 的定位是纯优化，所以这不该是终态。
    什么时候用它：只作为过渡/对照。如果方案 A 在真机上出了意外，用它回退验证。

  方案 C：把每枪的推进量做成"一次性推一段距离"而不是"推一段时间"。
    上升沿后给偏移量加一个固定增量（= 速率 × W 的等价值），仍然指数/限速释放。
    与方案 A 数学上接近，但引入"每枪一份量"的内部概念，容易再滑回"力度"那套
    命名，且释放曲线的时间常数又会变成一个隐藏参数（5.3 说明它可用行程很小）。
    评价：不推荐，除非方案 A 在实现上遇到 latch 与回落逻辑打架的问题。

建议：实现【方案 A】。它同时满足两件事 —— 参数收敛成两个（第一节的要求），
以及把上游那个按压时长漂移修掉（"纯优化"的定位）。把 W 的取值和"连点每枪
推进量 = 速率 × W"这个关系明确告知用户，让他真机上决定 W 要不要调整。
不要替他决定手感，也不要为了省事退到方案 B 就交付。

其他需要注意的：
  - 速度的标度：建议保留现有 HOLD_RATE_SLOW=30 / HOLD_RATE_FAST=150 (px/s)，
    50% = 90px/s。90px/s 正是上游 strength*3f @30fps 的等价值，那一版实机确认
    "有明显效果"，是个可靠的锚点。
  - 范围的标度：保留 RANGE_MAX_RATIO=0.37（满量程 0.37 屏高）+ MAX_OFFSET=600 保险。
  - 参考高度用 recoilRefHeight（FloatService 建立采集后写入 captureH），
    不要写死 1080。

7.1 构建走 GitHub Actions，本地没有 Android SDK
    .github/workflows/build.yml 的 push 触发只认 byo-model 和 master 两个分支。
    【特性分支必须靠 PR（pull_request 事件）或 workflow_dispatch 才会构建。】
    产物是 assembleDebug 的 app-debug artifact（约 92MB zip / 102MB apk）。

7.2 推送：本地没有 git 凭据，环境变量里有 GITHUB_MCP_TOKEN
    git -c credential.helper='!f() { echo username=x-access-token; \
        echo password=$GITHUB_MCP_TOKEN; }; f' push -u mine <branch>
    用 credential.helper 而不是把 token 拼进 URL（不进 argv、不写 .git/config）。
    远端：mine = love3025/YOLOVAIM，origin = 上游 xiangsu1145。
    注意：不要用 MCP create_or_update_file 推文件，GitHub API 会补 EOF 换行，
    造成本地与远端永久分叉。

7.3 装到设备：唯一通道是 ZeroTermux 的调试接口 http://127.0.0.1:19998
    每个请求要带 7 位匹配码（?code=XXXXXXX 或 header X-Zt-Ai-Debug-Code）。
    【匹配码每次重开调试开关都会变，必须让用户当场提供，不要写进任何文件。】
    注意接口的 HTTP 状态码恒为 200，真实结果在 body 的 {"ok":...} 里。
    单次请求上限约 110s。root/exec 是把命令喂给 sh 的 stdin，输出里总有一行
    无害的 "sh: <stdin>[1]: -c: inaccessible or not found"；别用嵌套 heredoc。

7.4 传 APK 到设备：容器和设备共享 loopback，不用切块 base64
    容器：python3 -m http.server 18777 --bind 127.0.0.1 --directory <dir>
    设备：curl -sS -o /data/local/tmp/yv.apk http://127.0.0.1:18777/<name>.apk
    然后 sha256sum 两边对一下。

7.5 换包会清掉模型和配置 —— 固定套路，顺序不能错
    每次 CI 构建的 debug 签名密钥都不同 → 必须卸载重装 → filesDir 全清
    （models/ 约 12MB + config.json）。

      P=/data/data/io.github.love3025.yolovaim
      cp -a $P/files /data/local/tmp/yv-files-bak     # 先备份！
      pm uninstall io.github.love3025.yolovaim
      pm install -r /data/local/tmp/yv.apk
      # 【重装后 uid 和 SELinux 类别都会变，必须重新读，不能套用旧值】
      U=$(stat -c %u:%g $P)
      CTX=$(ls -dZ $P | awk '{print $1}')
      mkdir -p $P/files
      cp -a /data/local/tmp/yv-files-bak/. $P/files/
      chown -R $U $P/files
      chcon -R "$CTX" $P/files                        # 不是 restorecon！
      ls -laZ $P/files/                               # 确认类别与父目录一致

    实测：一次重装后 uid 从 10546 变成 10547，MLS 类别从 c34 变成 c35。

    【为什么不能用 restorecon】它按 file_contexts 只恢复类型，会把文件打成裸
    u:object_r:app_data_file:s0，丢掉 per-app 的 MLS 类别。后果很阴：
    untrusted_app 不是 mlstrustedsubject，读裸 s0 文件靠 dominance 能过（模型能
    加载，看着一切正常），但写要求 level 相等 → config.json 保存静默失败。

7.6 服务必须让用户从界面手动启动
    注入器连接需要录屏授权，monkey 拉起进程不够。要看启动期日志得让用户手动启动。
    另外 logcat main 缓冲默认只有 256KB，会被系统进程刷屏约 30 秒冲穿，
    调试前先 logcat -G 16M（重启后失效）。

7.7 用完提醒用户关掉 ZeroTermux 的外部 AI 调试开关。
